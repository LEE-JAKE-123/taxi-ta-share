# P0 정산 경로 정정

관련 요구사항: `FR-35~40`, `FR-50`, `FR-52~54`, `TR-01~03`

## 적용한 경계

- 실제 요금 제출은 `IN_PROGRESS → SETTLEMENT_PENDING` 전이와 확정 예치 인원 스냅샷만 만든다. 이 시점에는 포인트 원장, 잔액, 참여 완료 상태를 변경하지 않는다.
- 새 정산은 `ESCROW_CONFIRMED` 예치 cohort를 사용한다. `NO_SHOW` 참여자도 분모와 정산 원장에 포함하며, 새 `BOARDED` 정산은 허용하지 않는다.
- 참여자는 실제 요금을 확인하거나 이의제기할 수 있다. 열린 이의제기가 있으면 최종 정산은 차단된다.
- 확인과 이의제기는 참여자별로 하나만 선택할 수 있다. 같은 정산 행 잠금과 DB 트리거가 동시 요청도 직렬화하며, 이미 기록된 확인의 재시도는 확인 기한 뒤에도 무해하게 처리한다.
- 최종 정산은 전원 확인 또는 서버가 판단한 확인 기한 경과 뒤 방장 요청으로만 실행한다. 원장·잔액·참여자·모집·정산 상태는 하나의 직렬화 트랜잭션에서 변경한다.

## 데이터베이스 변경

`0014_confirmed_cohort_settlement.sql`은 과거 `BOARDED` 정산을 수정하지 않는다. 기존 `ESCROW_CONFIRMED` 정산에는 누락된 cohort 스냅샷만 보강하고, 이후 원장 insert는 `SETTLEMENT_PENDING`과 `PENDING_CONFIRMATION` 상태 및 확정 cohort 금액을 만족해야 한다.

## 남은 열린 결정

- 확인 기한(현재 24시간 기술값)의 제품 승인 및 자동 실행 스케줄러
- 취소 수수료·환불, 노쇼 추가 제재, 반올림 초과분 부담 정책

이 항목들은 정책 확정 전에는 자동 정산·관리자 강제 판정을 임의로 추가하지 않는다.

## 이의제기 MVP 정책

- 이의제기는 참여자가 확인 기한 안에 철회할 수 있으며, 철회 이력은 삭제하지 않는다.
- 활성 관리자만 이의를 기각하거나 수정 요금 재제출을 요청할 수 있다. 기각 후에는 기존 실제 요금의 확인·정산을 재개한다.
- 수정 요금 재제출 요청은 아직 원장·잔액이 바뀌지 않은 정산 제안만 무효화한다. 방장은 새 실제 요금을 제출하고, 이전 확인은 지운 뒤 새 확인 기한을 시작한다.
- 하나의 이동에 열린 이의가 여러 건이면 모든 이의를 처리하기 전에는 수정 요금을 요청할 수 없다.

## 실제 요금 입력자 MVP 정책

- 방장은 출발 전 예치가 완료된 확정 참여자 한 명을 실제 요금 입력자로 지정할 수 있으며, 방장은 언제나 입력 권한을 유지한다.
- 지정 변경은 `CONFIRMED` 상태에서만 가능하고, 출발 뒤에는 지정 당시 권한만 사용한다.
- 수정 요금 재제출은 이의 해결 흐름의 방장 전용 권한으로 유지한다.
