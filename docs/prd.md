# PRD — 택시타쉐어

- **문서 버전:** v0.7
- **작성일:** 2026-07-28
- **제품명:** 택시타쉐어
- **팀명:** 택시타쉐어
- **네이밍 의미:** “택시 타다”와 “공유하다(Share)”를 결합한 이름으로, 같은 방향의 대학생이 택시를 함께 타고 비용을 나누는 서비스의 핵심 기능을 표현한다.
- **문서 목적:** 대학생이 동일하거나 인접한 목적지로 이동할 때 검증된 학내 구성원과 택시에 동승하고, 택시비를 공정하게 분담할 수 있는 MVP의 요구사항을 정의한다.

---

## 1. 제품 개요

### 1.0 브랜드 정의
**택시타쉐어**는 대학생이 같은 방향으로 이동할 때 함께 택시를 타고 비용을 공유하도록 연결하는 서비스이자, 이를 만드는 팀의 이름이다. 이름 자체가 “택시를 타다”와 “쉐어(Share)하다”를 결합해 제품이 제공하는 동승·비용 분담 경험을 직관적으로 설명한다.


### 1.1 문제 정의
대학생은 귀가, 통학, 행사장 이동 등에서 택시를 자주 이용하지만, 혼자 탑승할 경우 비용 부담이 크다. 반면 비슷한 시간대에 같은 방향으로 이동하는 학생을 찾기 어렵고, 낯선 사람과의 동승에는 신원·정산·노쇼에 대한 불안이 따른다.

### 1.2 해결 방식
첫 이용자(방장)가 출발지·도착지·출발 시간을 설정해 방을 만들면, 서비스의 **AI 매칭 추천 기능**이 출발지 주변에서 동일 또는 인접 목적지로 이동하려는 가입 사용자를 분석해 가장 적합한 방을 추천한다. 2~4명이 확정되면 한 대의 택시에 함께 탑승하며, 택시비는 서비스 내 포인트를 통해 인원수 기준으로 분담한다.

### 1.3 기존 방식과의 차별점
기존 택시 이용은 대체로 한 명이 한 대의 택시를 이용하고 비용을 전액 부담하는 방식이어서, 같은 시간대에 같은 방향으로 이동하는 대학생에게도 비용 절감 기회가 연결되지 않았다. **택시타쉐어는 택시 동승 그룹을 만들고 인원수 기준으로 비용을 나누는 기능**을 핵심으로 제공해 이 개인 부담을 해결한다.

| 구분 | 기존 개인 택시 이용 | 택시타쉐어 |
|---|---|---|
| 이동 방식 | 개인이 단독 탑승 | 같은 방향의 가입 대학생 2~4명이 동승 |
| 비용 부담 | 한 사람이 택시비 전액 부담 | 참여 확정 인원 기준으로 비용을 분담 |
| 동승자 탐색 | 개인이 직접 찾아야 하거나 탐색 수단이 없음 | AI가 출발지·도착지·시간·우회 부담을 분석해 방을 추천 |
| 노쇼 대응 | 사전 합의·보상 체계가 없음 | 포인트 예치와 확정 인원 기준 정산으로 부담을 관리 |

### 1.4 제품 원칙
1. **가입 정보 기반 이용:** 학번·이름·성별·학교 이메일을 입력해 가입한 대학생만 이용한다. MVP에서는 학교 이메일의 인증 절차를 요구하지 않는다.
2. **매칭의 명확성:** 출발·도착·시간·예상 분담금이 확정 전에 모두 보인다.
3. **AI 보조 매칭:** AI가 목적지 간 거리, 출발지 근접도, 시간 차이와 모집 상태를 비교해 이해 가능한 추천 사유를 제시한다.
4. **선결제 기반 약속:** 참여 확정 시 포인트를 예치하여 노쇼 리스크를 낮춘다.
5. **공정한 정산:** 도착 후 실제 택시비를 기준으로 최종 분담금을 계산한다.
6. **안전한 동승:** 최소한의 연락처 노출과 신고·차단 기능을 제공한다.

## 2. 목표 및 성공 지표

### 2.1 제품 목표
- 대학생이 2~4인 단위로 빠르고 안전하게 택시 동승 그룹을 만들 수 있게 한다.
- 혼자 택시를 이용하는 경우 대비 개인의 이동비 부담을 낮춘다.
- 선결제와 노쇼 규칙을 통해 매칭 확정 후 이탈을 최소화한다.

### 2.2 비목표(MVP 범위 제외)
- 택시 호출 사업자 자체 운영 또는 택시 배차 직접 제공
- **실제 카드결제, PG 연동, 포인트 유상 충전·현금 환불 등 실금액 결제 기능**
- 운전자 매칭, 자가용 카풀, 장거리 정기 카풀
- 서로 다른 대학 간 광역 서비스의 동시 출시
- 복잡한 거리별·하차순서별 정산 로직

### 2.3 핵심 지표(KPI)
| 구분 | 지표 | 정의 |
|---|---|---|
| 매칭 | 매칭 성사율 | 생성된 모집 중 최소 2인 출발이 확정된 비율 |
| 이용 | 완료 이동 건수 | 실제 도착 및 최종 정산까지 완료된 이동 수 |
| 효율 | 평균 탑승 인원 | 완료 이동 1건당 평균 탑승자 수 |
| 신뢰 | 노쇼율 | 확정 후 집결 시각까지 미도착한 참여자 비율 |
| 경험 | 재이용률 | 첫 완료 이동 후 30일 내 재이용한 사용자 비율 |
| 정산 | 정산 오류율 | 고객 문의 또는 조정이 발생한 최종 정산 비율 |

## 3. 대상 사용자

### 3.1 핵심 타깃
- 캠퍼스 내·외 이동, 막차 이후 귀가, 공항·터미널·행사장 이동 수요가 있는 대학생
- 택시비 절감은 원하지만 불특정 다수와의 거래에는 불안함을 느끼는 학생
- 학교 이메일 또는 학생 신분 확인 수단을 보유한 사용자

### 3.2 사용자 페르소나

**페르소나 A — 귀가 비용을 아끼고 싶은 학생**
- 야간 수업 또는 동아리 활동 후 귀가한다.
- 택시를 타야 하지만 혼자 부담하기에는 요금이 부담스럽다.
- 같은 방향의 신뢰 가능한 동승자를 빨리 찾고 싶다.

**페르소나 B — 약속 시간에 민감한 모집자**
- 공항·터미널·공연장 등 특정 시각까지 가야 한다.
- 동승자를 모집하되 출발 시각이 지연되는 것은 원하지 않는다.
- 확정 후 이탈하거나 나타나지 않는 참여자에 대한 보상을 원한다.

## 4. 사용자 시나리오

1. 사용자는 학번·이름·성별·학교 이메일을 입력해 회원가입한다.
2. 첫 이용자(방장)가 출발지, 도착지, 출발 시각, 최대 인원(2~4명)을 입력해 방을 만든다.
3. 시스템은 방장의 출발지 주변에 있고 동일 또는 인접 목적지·유사한 출발 시각을 희망하는 사용자에게 AI 기반으로 해당 방을 추천한다.
4. 추천을 받은 가입 사용자는 방의 출발지·도착지·출발 시각·예상 분담금을 확인하고 입장 신청한다.
5. 방장이 승인하거나 자동 승인 조건을 충족하면 참여자가 확정된다.
6. 방은 출발 시각이 되면 자동으로 닫히며, 방장은 출발 시각 전이라도 모집을 중간에 닫을 수 있다.
7. 확정 인원은 예상 요금의 인원수 기준 분담액을 포인트로 예치한다. 가용 포인트가 부족하면 보유분만 예치하고 부족분은 해당 참여자의 추적 가능한 예치 부족분으로 기록하되, 다른 참여자에게 재배분하지 않는다.
8. 최소 2명 이상이 확정된 닫힌 방은 출발 가능 상태가 되며 집결 정보와 동승 채팅방이 열린다.
9. 참여자들은 집결지에서 택시를 함께 이용한다.
10. 목적지 도착 후 실제 택시비를 입력·확인하고, 실제 요금을 기준으로 최종 정산한다.
11. 노쇼가 발생한 경우에도 확정 인원을 기준으로 정산하며, 노쇼자의 예치금은 규정에 따라 사용된다.

### 5.3.1 AI 매칭 추천 로직

AI는 방에 입장하려는 사용자의 출발지·도착지·희망 출발 시각을 기준으로, 현재 열려 있는 후보 방을 탐색하고 후보별 적합도를 계산해 추천한다. AI의 역할은 **후보 탐색·순위화·추천 사유 설명**이며, 최종 참여와 출발 여부는 항상 사용자가 결정한다.

**초기 매칭 기준(정책값, 운영 중 조정 가능)**
- 출발지 후보 반경: 기본 300m
- 도착지 인접 허용 반경: 기본 500m
- 출발 시각 허용 범위: 희망 시각 전후 15분
- 방 입장 가능 조건: 잔여 좌석이 1석 이상이고 모집 상태가 OPEN인 방만 추천
- 우선순위: 동일 도착지 > 도착지 간 거리 및 예상 우회시간이 적음 > 출발 시각 차이가 적음 > 사용자의 출발지와 방 출발지가 가까움 > 출발 임박도
- 사용자 중심 제한: 사용자에게 불리한 우회 시간 또는 출발지 이동 거리가 기준값을 초과하는 후보는 추천에서 제외하거나 낮은 우선순위로 표시

**추천 문구 예시**
- “희망하신 A장소에서 **230m** 떨어진 B장소로 이동하는 2인 방이 있습니다.”
- “출발지는 현재 위치에서 **120m**, 출발 예정 시각은 **10분 후**입니다.”
- “동일 목적지로 가는 모집보다 예상 우회 시간이 **3분 적습니다**.”

> 인접 목적지 동승은 실제 경로와 이동 시간이 달라질 수 있다. AI는 인접 목적지 후보를 추천할 때 목적지 거리뿐 아니라 예상 우회 거리·시간을 함께 표시해야 하며, 모집자가 경유를 허용한 경우에만 해당 후보를 노출한다.

#### 5.4.1 MVP 포인트 운영 정책

MVP의 포인트는 **실제 화폐나 카드결제를 대체하는 서비스 내 가상 정산 단위**다. 개발 기간과 결제 연동 범위를 줄이기 위해 카드 결제, PG 연동, 유상 충전, 현금 환불은 구현하지 않는다. 포인트는 사용자가 직접 충전하는 방식이 아니라 **관리자가 특정 사용자 계정에 지급하는 방식**으로만 제공한다.

- 사용자는 포인트를 직접 구매·충전·환전할 수 없다.
- 관리자는 운영 화면에서 대상 계정과 포인트 금액·지급 사유를 지정해 지급 실행을 기안한다. 다른 활성 관리자가 이를 승인한 뒤, 기안 관리자가 원장 지급을 실행한다. 기안자와 승인자는 같을 수 없으며, 자신의 계정 또는 자신의 요청에는 지급할 수 없다.
- 모집 확정 전 예치에서 참여자의 가용 포인트가 1인 예치금보다 적으면, 가용분만 일반 포인트에서 예치하고 정확한 부족분을 해당 참여자의 append-only 예치 부족분으로 기록한다. 이 기록은 현재 모집의 `CONFIRMED`·집결·이동을 막지 않지만, 부족분이 남아 있는 사용자의 다른 모집 생성·신청·예치는 막는다.
- 예치 부족분은 예상 요금의 임시 약정이며, 실제 요금 잠정 정산에서 해당 참여자의 실제 분담금·예치금·가용 포인트를 기준으로 상계한다. 실제 정산 부족분만 기존 외상으로 남기며, 예상 예치 부족분과 이중 청구하지 않는다.
- `HOST_NO_START`로 비귀책 확정 참여자의 예치금을 반환할 때 그 참여자의 미상환 예치 부족분도 함께 면제한다. 모집자 부담과 패널티는 별도 정책을 따른다.
- 포인트는 앱 내에서만 사용하며 현금·카드 결제수단과 교환되지 않는다.
- 실제 택시 기사에게 지급하는 요금은 MVP 서비스의 결제 범위 밖이다.
- 서비스는 **예상 요금과 실제 요금에 대응하는 포인트 정산 로직**을 검증하는 데 집중한다.
- 향후 정식 출시에서 실결제를 도입할 경우, 관련 법률·결제대행·환불·부정거래 대응 정책을 별도 설계한다.

#### 5.4.2 정산 계산식

- 예상 총 요금: $E$
- 실제 총 요금: $A$
- 정산 대상 인원: $N$
- 1인 예치금: $D = \lceil E/N \rceil$
- 개인별 최종 부담액: 방장부터 참여 승인 시각 오름차순(동률은 사용자 ID
  오름차순)으로 정렬한다. 앞의 $N - (A \bmod N)$명은
  $\lfloor A/N \rfloor$, 나머지는 $\lfloor A/N \rfloor + 1$을 부담한다.
- 사용자별 반환/추가 차감액: $D - F_i$

금액의 나눗셈에서 발생하는 잔여 포인트는 방장과 먼저 참여 승인된 사용자부터
1포인트 단위 혜택을 받도록 배분한다. 개인별 부담액의 합은 항상 실제 총요금과
같아야 한다.

#### 5.4.3 예시
- 예상 택시비: 18,000포인트
- 확정 인원: 3명
- 1인 예치금: 6,000포인트
- 실제 택시비: 15,000포인트
- 1인 최종 부담액: 5,000포인트
- 결과: 각 참여자에게 1,000포인트 반환

### 5.5 노쇼 및 취소 정책

| 상황 | 기본 처리 정책 |
|---|---|
| 모집 마감 전 참여 취소 | `OPEN`이며 출발 전이고 예치 전인 신청·승인 참여자만 비용 없이 취소 가능 |
| 모집 종료 또는 예치 후 취소 | 방장이 모집을 종료하거나 출발 시각이 지나면 참여 취소 불가. 예치 완료 뒤에는 취소·환불·정산 인원 변경을 허용하지 않으며 확정 인원을 정산 대상으로 유지 |
| 노쇼 | **확정 인원을 정산 대상 인원으로 유지**하며, 노쇼자도 자신의 최종 분담액을 부담 |
| 실제 탑승 인원이 확정 인원보다 적은 경우 | 실제 총 택시비를 확정 인원수로 나누어 정산. 노쇼자의 부담분은 동승자에게 재배분하지 않음 |
| 모집자 노쇼 또는 이동 미개시 | 책임 확정 후 모집을 `CANCELLED`로 전이하고 비귀책 확정 참여자의 예치금은 전액 반환한다. 모집자 예치금 및 패널티는 별도 정책으로 처리 |
| 실제 요금 이의 제기 | 증빙 제출 및 운영자 검토 절차 제공 |

**노쇼 핵심 원칙:** 사용자가 참여를 확정하고 예치금을 납부한 경우, 집결 시각까지 도착하지 않더라도 해당 사용자는 정산 대상에서 제외되지 않는다. 이는 현장 탑승자의 비용 부담 증가를 방지하기 위한 정책이다.

**정책상 결정이 필요한 항목**
1. 노쇼자 예치금 중 최종 분담액을 초과하는 금액을 전액 반환할지, 일부를 노쇼 수수료로 차감할지
2. 모집자 또는 참여자에게 귀책이 있는 취소의 기준과 증빙 방식
3. 택시가 출발하지 못한 경우의 전액 환불 기준
4. 반복 노쇼에 대한 이용 제한 단계

MVP 권장안은 “노쇼자도 실제 비용의 확정 인원 기준 분담액을 부담하고, 추가 노쇼 수수료는 초기에는 부과하지 않음”이다. 사용성 데이터를 확보한 뒤 반복 노쇼에 한해 단계적 제재를 도입한다.

#### 5.5.1 귀책자 부담·비귀책자 보호 원칙

취소, 이동 미개시, 노쇼, 허위 요금 또는 운영자 지급 오남용에서 귀책이
확정된 사용자는 해당 행위로 생긴 정책상 부담과 이용 제한을 부담한다.
비귀책 확정 참여자는 예치금 전액 반환 또는 기존 확정 인원 기준 정산을
보장받으며, 귀책자의 비용·외상·제재가 이들에게 재배분되지 않는다.

- 귀책은 서버 기록과 허용된 증빙, 당사자의 반박 기회, 운영자 또는 사전
  정의된 서버 규칙의 판정으로만 확정한다. 방장 또는 한 참여자의 단독
  주장만으로 추가 차감이나 이용 제한을 실행하지 않는다.
- 실제 이동이 시작된 경우에는 확정 예치 인원(노쇼 포함)을 유지해 정산하며,
  노쇼자의 부담을 동승자에게 재배분하지 않는다.
- 노쇼 신고는 사건 접수일 뿐 최종 판정이 아니다. 신고 대상은 반박 또는
  증빙을 제출할 수 있고, 최종 확정 전에는 추가 차감·이용 제한을 적용하지
  않는다.
- `START_REVIEW`가 기록되면 신고 대상에게 인앱 반박 기회를 게시하고, 게시
  시각부터 10분의 반박 기한을 서버 기록으로 보존한다. 반박이 제출되었거나
  기한이 지난 뒤에만 운영자가 귀책 사실을 확정할 수 있다. 통지·기한 경과는
  자동 확정이나 자동 금전 처리를 의미하지 않는다.
  기존 검토 기록에 게시 증거가 없으면 활성 비당사자 관리자가 새 게시 기록을
  남긴 뒤에만 반박·무응답 책임 확정을 진행할 수 있다.
- 이동이 시작되지 않은 경우에는 비귀책 참여자의 예치금을 먼저 전액 반환한다.
  귀책자의 보류·차감·외상·이용 제한은 별도 책임 판정과 append-only 원장
  명령으로 처리한다.
- 이 MVP에서는 `HOST_NO_START` 책임이 확정된 뒤 운영자가 별도 실행으로
  모집을 `CANCELLED`로 전이하고 비귀책 확정 참여자(`MEMBER`)의 예치금만
  전액 반환한다. 모집자 예치금·패널티·이동 미시작 유예 시간은 이 실행으로
  정하지 않으며, 별도 정책과 append-only 명령으로만 처리한다.
- 열린 실제 요금 이의가 있는 동안 최종 정산과 귀책 제재를 확정하지 않는다.
  이의 제기 자체에는 벌점이나 차감을 부과하지 않으며, 허위·조작이 확정된
  제출자만 책임 대상이 될 수 있다.
- 출발 시각 이후에는 `CLOSED` 모집을 예치 확정하거나 새 참여·승인을 할 수
  없다. 예치 확정에 실패한 모집은 출발시켜서는 안 되며, 보류 포인트는
  멱등적으로 반환되어야 한다.
- 관리자 포인트 지급은 지급 사유·대상·근거·실행자·승인 기록을 남겨야 한다.
  실행자와 승인자는 분리하고, 자기 자신 또는 자신의 요청을 승인·지급할 수
  없다. 오지급은 과거 원장을 수정하지 않고 보정 원장으로만 처리한다.

책임 금액·이용 제한 기간·이동 미시작 유예 시간·증빙 보관 기간은 출시 전에
정책 버전으로 별도 승인한다. 값이 확정되기 전에는 자동 추가 금전 제재 대신
비귀책자 보호, 사건 기록, 운영자 판정과 이용 제한만 적용한다.

### 6.2 모집 생성 흐름
`홈 → 출발지 설정 → 도착지 설정 → 출발 시각/목표 인원 설정 → 예상 요금 확인 → 모집 게시 → 참여자 확정 → 포인트 예치 → 집결/이동`

### 6.3 참여 흐름
`홈/추천 모집 → 모집 상세 → 예상 분담금·노쇼 정책 확인 → 참여 신청 → 승인 또는 자동 확정 → 포인트 예치 → 그룹 채팅/집결 → 이동 → 최종 정산`

### 6.4 정산 흐름
`도착 → 실제 요금 입력 및 증빙 첨부 → 참여자 확인 → 최종 분담금 산정 → 예치금 반환 또는 부족분 차감 → 거래 내역 확인`

## 8. 기술 아키텍처 및 구현 원칙

### 8.1 기술 스택

| 영역 | 기술 | 적용 범위 |
|---|---|---|
| 프론트엔드·애플리케이션 서버 | **Next.js** | 사용자 웹/모바일 웹 UI, 서버 렌더링, API 라우트, 회원가입 흐름, 매칭·정산 오케스트레이션 |
| 지도·경로 API | **네이버 지도 API 또는 카카오맵 API** | 출발지·도착지 검색, 예상 거리·소요 시간·택시비 산정. 제공자는 추후 변경 가능 |
| 데이터베이스 | **Neon DB(네온디비)** | 사용자·모집·참여·포인트 원장·정산·신고 데이터의 영속 저장 |
| 배포·호스팅 | **Vercel(버쎌)** | Next.js 애플리케이션 빌드, 배포, 프리뷰 환경, 서버리스 실행 환경 |

> **확인 필요:** Neon DB는 PostgreSQL 기반 서버리스 데이터베이스로 사용한다. 운영 리전, 연결 풀링 방식, 백업·복구 정책 및 개발·프리뷰·운영 환경별 데이터베이스 분리 방식은 개발 착수 전에 확정한다.

### 8.2 논리 아키텍처

1. **Next.js 클라이언트:** 위치·모집·참여·포인트·정산 화면을 제공한다.
2. **Next.js 서버/API 계층:** 로그인 세션·접근 권한 검증, 모집 상태 전이, AI 추천 요청 조합, 정산 계산 및 포인트 원장 기록을 처리한다.
3. **AI 매칭 모듈:** 열려 있는 후보 방을 조회한 뒤 사용자 출발지와 방 출발지의 거리, 목적지·시간·인원·경유 허용 여부를 입력으로 적합도를 산정하고 추천 문구를 생성한다.
4. **Neon DB(네온디비):** 핵심 업무 데이터와 변경 이력을 저장한다. 포인트 잔액은 관리자 지급·예치·반환·정산을 포함한 원장 기반으로 관리한다.
5. **Vercel:** 배포 환경을 제공하며, 환경 변수로 DB 연결 정보와 외부 지도 API 키를 분리 관리한다.

### 8.3 구현 요구사항

| ID | 요구사항 | 우선순위 |
|---|---|---|
| TR-01 | Next.js 서버 측에서 모든 포인트 예치·환불·추가 차감 요청의 권한과 잔액을 검증해야 한다. | Must |
| TR-02 | 포인트 거래와 정산 완료 처리는 데이터베이스 트랜잭션으로 원자적으로 기록해야 한다. | Must |
| TR-03 | 결제·정산 API에는 멱등성 키를 적용해 중복 요청으로 인한 중복 차감을 방지해야 한다. | Must |
| TR-04 | AI 추천은 후보 모집 데이터와 거리 계산 결과를 근거로 해야 하며, 근거 없는 목적지·요금 정보를 생성해서는 안 된다. | Must |
| TR-05 | AI 추천 결과에는 후보 ID, 계산된 거리, 산정 시각, 추천 사유를 저장 또는 추적 가능하게 해야 한다. | Should |
| TR-06 | Vercel 배포 환경은 개발·프리뷰·운영 환경을 분리하고, 비밀값은 환경 변수로만 관리해야 한다. | Must |
| TR-07 | 데이터베이스는 정기 백업·복구 절차와 운영 모니터링 방안을 갖춰야 한다. | Must |
| TR-08 | 지도 API 제공자 변경 가능성을 고려해 거리·시간·예상 요금 산정 모듈을 API 제공자에 종속되지 않도록 추상화해야 한다. | Should |

## 10. 상태 정의

### 9.1 모집 상태
- **DRAFT:** 작성 중
- **OPEN:** 참여자 모집 중(출발 시각 전, 방장이 수동 종료하지 않은 상태)
- **CLOSED:** 출발 시각 도래 또는 방장 수동 종료로 신규 입장이 닫힌 상태
- **CONFIRMED:** 모집 종료 후 최소 인원 충족 및 참여 확정, 보유 포인트 예치와 필요한 참여자별 예치 부족분 기록 완료
- **IN_PROGRESS:** 집결 또는 이동 시작
- **SETTLEMENT_PENDING:** 실제 요금 입력 후 동의 또는 이의제기 대기. 10분 뒤
  포인트 처리는 잠정 정산될 수 있으며 24시간 이의 기간이 끝날 때까지 유지
- **COMPLETED:** 이의제기 기한 만료 및 모든 이의 처리 후 최종 정산 완료
- **CANCELLED:** 모집 취소
- **EXPIRED:** 출발 시각까지 최소 인원 미충족, 모집 종료 시 최소 인원 미충족,
  또는 출발 시각까지 예치 확정을 완료하지 못한 모집

### 9.2 참여자 상태
- **APPLIED:** 참여 신청
- **APPROVED:** 참여 승인
- **DEPOSITED:** 예치 완료
- **CHECKED_IN:** 집결 확인
- **NO_SHOW:** 집결 시각까지 미도착
- **COMPLETED:** 정산 완료
- **CANCELLED:** 참여 취소

## 11. MVP 범위 및 출시 단계

### 10.1 MVP (1개 대학 또는 1개 캠퍼스 파일럿)
- 학번·이름·성별·학교 이메일 입력 기반 회원가입(별도 인증 절차 없음)
- 방장의 출발지·도착지·출발 시각·최대 인원 기반 방 생성
- 출발 시각 자동 종료 및 방장의 수동 모집 종료
- AI 기반 동일/인접 도착지 및 시간대 기반 방 추천과 거리·우회시간·추천 사유 표시
- 2~4인 참여 및 확정
- 실제 카드결제 및 사용자 직접 충전 없이, 관리자가 지급한 자체 포인트 기반의 예상 요금 예치·실제 요금 기반 최종 정산 시뮬레이션
- 노쇼 표시 및 확정 인원 기준 정산
- 기본 푸시 알림, 신고·차단, 거래 내역

### 10.2 후속 단계
- 지도 기반 실시간 집결 확인 및 안전 귀가 기능
- 택시 호출 플랫폼 연동 및 요금 자동 수집
- 영수증 자동 인식 또는 요금 검증 고도화
- 신뢰 점수·반복 노쇼 제재·우수 이용자 혜택
- 학교 행사·축제·방학 귀성 수요를 위한 예약 모집
- 다중 경유지에 대한 공정 정산 알고리즘

## 14. 출시 승인 기준

다음 조건을 충족해야 MVP 파일럿을 출시한다.

- 필수 가입 정보(학번·이름·성별·학교 이메일)를 입력하지 않은 사용자가 방 생성·참여·포인트 거래를 수행할 수 없다.
- 2~4명 인원 제한과 최소 2명 출발 조건이 모든 핵심 흐름에서 적용된다.
- 예상 요금 기반 예치, 실제 요금 기반 최종 정산, 차액 반환/추가 차감이 거래 원장에 정확히 기록된다.
- 노쇼 발생 시 확정 인원 기준 정산이 일관되게 적용된다.
- AI 추천이 동일·인접 목적지 후보 방에 대해 계산된 거리, 허용 여부 및 추천 사유를 사용자에게 표시한다.
- 방은 출발 시각에 자동으로 닫히며, 방장의 수동 종료 후에도 신규 입장이 차단된다.
- 포인트 원장·정산 처리의 트랜잭션과 중복 요청 방지 정책이 검증된다.
- 실제 카드결제·사용자 직접 충전·현금 환불 없이, 관리자 지급 포인트로 전체 예치·반환·정산 흐름이 동작한다.
- 네이버 지도 API 또는 카카오맵 API를 통해 예상 거리·소요 시간·택시비가 산정되며, 제공자 변경이 가능하도록 구현된다.
- 모집 취소, 참여 취소, 최소 인원 미충족, 포인트 부족, 실제 요금 이의제기 등 예외 상황이 정의되어 있다.
- 신고·차단·고객 문의 접수 및 운영자 검토 흐름이 준비되어 있다.
- 개인정보·위치정보·포인트 운영 구조에 대한 법률 및 결제 정책 검토가 완료되어 있다.
